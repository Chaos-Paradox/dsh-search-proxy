# 宿主兼容与发布测试约定

[English](host-compatibility.md) | 中文

本约定适用于后续插件更新。目标是保留已支持宿主的行为，并在扩大支持范围前取得可复现的证据。`AGENTS.md` 与 PR 模板引用本文件。

## 版本约定

| 角色 | 当前约定 | 更新方式 |
|---|---|---|
| 最低支持版 | 未打补丁的 DSH `0.2.1-alpha.2` | 后续更新持续回归；提高最低要求需明确记录兼容性破坏与升级路径，不在修补版中悄悄修改。 |
| 推荐版 | 当前同为 `0.2.1-alpha.2` | 新版通过真实宿主、发布包和设置页验证后，才更新推荐版。 |
| 新版使用反馈 | DSH `0.2.1-rc.3`，维护者于 2026-10-26 反馈实测通过（未晋升推荐版） | 具体反馈与证据范围见下节；扩大正式验证矩阵前仍需补齐精确构建和检查记录。 |
| 上游开发分支 | 不作为支持承诺 | 可选观察任务；每次固定实际提交。失败用于提前发现接口变化，不自动放宽依赖或阻断基准版发布。 |

最低版与推荐版相同只运行一次。推荐版以后发生变化时，两个版本都必须保留，不能只测最新版。候选测试失败后需记录原因并决定修复或暂不支持，不能把已知失败的候选写成兼容版本。

当前固定基准：

- 上游仓库：<https://github.com/deepseek-ai/deepseek-harness>
- 发布标签：[`dsh-v0.2.1-alpha.2`](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.1-alpha.2)
- 提交：`d743267388641bc76f17c45ce8b4c231aed1d32c`
- 使用标准 base/Web bundle，不打宿主补丁，不使用兼容性豁免。

当前 DSH peer 范围为 `>=0.2.1-alpha.2 <0.3.0`，开发依赖固定在 `0.2.1-alpha.2` 列车。这个范围是安装声明，不是范围内所有版本均已测试的承诺。`@deepseek-ai/cordis` 等独立版本包按其自身发布版本处理。检查当前事实时，以 `package.json` 和具体构建的验证记录为准。

### DSH 0.2.1-rc.3 使用反馈（2026-10-26）

维护者确认当前插件在 DSH `0.2.1-rc.3` 上已实测可用。本次 README 更新据此列出该版本；对话中未附宿主精确构建提交、系统／架构、命令日志和逐项覆盖范围，因此这是维护者的实测反馈，不表示本次文档维护重新执行了完整组合与发布验收。

最低支持版、推荐版、peer 声明和已发布验证记录保持原约定。`rc.3` 的完整可复现验证记录补齐后，再按本约定决定是否晋升推荐版；不把这一反馈扩展为其他版本或所有平台均已验证。

## 哪些改动需要检查

代码、依赖、构建、bundle、安装流程变更应通过现有 CI。以下改动还应在合并前运行真实宿主组合测试：Web 服务接口、设置保存、客户端注入或 RPC、凭据读写、子进程接口、启停清理、配置层优先级、搜索路由及官方备用。发布前无论是否扩大宿主范围，都执行下面的发布检查。

只修改文档时，检查链接、版本号、命令和支持状态是否一致；不要求重新下载运行环境或运行上游真实搜索。

## 分层测试方案

| 层级 | 检查内容 | 执行要求与当前工具 |
|---|---|---|
| 插件回归 | 类型、提供方、取消／重定向、鉴权、设置卡控制器、构建产物 | 代码更新运行 `typecheck`、`test`、`build`。现有 CI 在 Linux、macOS、Windows 的 Node 24 上执行。 |
| 真实宿主组合 | 加载 bundle、真实配置层、宿主设置／凭据、路由、启用禁用、卸载、结果限制 | 每个最低／推荐宿主运行 `test:host`；接口相关变更合并前运行，所有发布必跑。 |
| 托管服务 | 空缓存准备、HTTP 就绪、缓存重启、停止与插件退出清理 | 现有三系统 CI 执行 `test:managed`，用 `SEARXNG_SMOKE_SEARCH=0` 隔离上游引擎波动。它使用开发依赖中的公共子进程提供方，不能代替整套宿主组合验证。 |
| 发布包与设置页 | 实际 tarball 安装、标准 Web profile 启动、卡片渲染、保存、测试搜索、启停 | 每次发布在最低／推荐宿主的干净 profile 验证；至少记录一个系统上的完整 Web 流程，其他平台覆盖情况如实列出。 |
| 真实上游搜索 | 自托管或外部实例实际返回可引用来源 | 发布前至少完成一次有联网条件的验证，使用 `test:e2e` 或默认 `test:managed`；上游限流／引擎故障单独诊断，不能直接归因于宿主不兼容。 |

Node 最低声明为 `22.19`，当前 CI 只跑 Node 24。建议后续增加 Linux + Node `22.19.0` 的类型检查、单元测试与构建，Node 24 继续承担三系统托管生命周期测试。增加前不得声称这一 Node 组合已通过 CI。

### 可复现的本地命令

先准备固定版本、无本地修改且已构建的宿主。首次准备可在一次性目录执行以下 macOS/Linux shell 示例；Windows 使用相应路径和环境变量语法：

```sh
git clone --depth 1 --branch dsh-v0.2.1-alpha.2 https://github.com/deepseek-ai/deepseek-harness.git /tmp/dsh-host-0.2.1-alpha.2
git -C /tmp/dsh-host-0.2.1-alpha.2 rev-parse HEAD
git -C /tmp/dsh-host-0.2.1-alpha.2 status --short
pnpm --dir /tmp/dsh-host-0.2.1-alpha.2 install --frozen-lockfile
pnpm --dir /tmp/dsh-host-0.2.1-alpha.2 run build
```

确认提交符合上面的约定；构建宿主使用其 `packageManager` 声明的 pnpm 版本。若已有符合约定的已构建 checkout，可复用，无需每次重建宿主。回到本插件目录，使用本项目所需的 pnpm 执行：

```sh
pnpm install --frozen-lockfile
pnpm run typecheck
pnpm test
pnpm run build
DSH_SOURCE_ROOT=/tmp/dsh-host-0.2.1-alpha.2 pnpm run test:host
SEARXNG_SMOKE_SEARCH=0 pnpm run test:managed
mkdir -p /tmp/searxng-release-check
pnpm pack --pack-destination /tmp/searxng-release-check
```

托管服务真实搜索或外部实例真实搜索任选符合实际部署的路径：

```sh
pnpm run test:managed
SEARXNG_BASE_URL=http://127.0.0.1:8080 pnpm run test:e2e
```

后一命令要求该外部实例已运行且开启 JSON；它不会自动启动实例。真实搜索需联网。CI 的 `SEARXNG_SMOKE_SEARCH=0` 结果不能代替真实搜索结果。

### 发布包与 Web 卡片验收

在每个目标宿主创建一次性标准 Web profile，用上一步实际生成的 tarball 绝对路径安装，记录完整命令与 tarball 校验和。不要复用开发目录软链接或用户真实 profile。宿主必须按目标版本的正常机制解析插件 peer，不能从插件开发目录借用基准版依赖。

1. 安装、启用并启动 profile：无缺失接口／注入错误，默认路由选择 SearXNG；更高优先级用户配置仍有效。
2. 本地模式：卡片准备至可用，自动端口正确；保存引擎／语言对下一次搜索生效；修改端口后重启，停止／退出后自有端口不可达。
3. 外部模式：无鉴权服务正常返回；受保护的本地测试端点拒绝缺少或错误凭据，正确自定义请求头后成功。密钥不出现在普通配置或读取响应，切换地址／挂载路径／头名后不复用原目标凭据；本地模式与官方备用不携带实例凭据。
4. 禁用、重新启用和卸载：路由按剩余配置层恢复，设置按设计保留，没有遗留自有服务进程。
5. 搜索失败与取消：明确报告错误；默认不调用付费提供方。官方备用能力按目标宿主的公开接口测试，缺失时说明限制，不能让测试通过修改宿主私有实现。

## 新宿主如何进入矩阵

1. 读取上游发布说明，重点检查 `ctx.web`、settings、credentials、subprocess、client 注入、RPC 和 bundle 机制。记录候选精确版本／标签／提交。
2. 在隔离宿主与 profile 中安装同一插件 tarball；候选不得改写基准宿主或真实用户配置。必要时用候选宿主的依赖做单独类型／构建检查，不能靠混用发布列车绕过 peer 问题。
3. 扩展真实组合测试为版本矩阵。当前 `tests/host-composition.mjs` 默认固定基准 `0.2.1-alpha.2`，可通过环境变量指定精确候选运行时，并断言目标没有 `searchWithProvider`；增加目标时核对版本与能力预期，并保持原基准用例。仅删除断言、跳过失败测试或改版本号不算兼容修复。
4. 对最低版和候选分别执行组合、发布包、Web 卡片与相关生命周期验证。候选如支持新的可选接口，分别测试成功路径和旧宿主的缺失能力路径。
5. 通过后更新本文件的版本角色、README、配置说明和必要的 peer 声明，留下新验证记录；未通过则记录未支持或受限的具体行为。

## CI 扩展建议与当前边界

当前 `.github/workflows/test.yml` 已自动执行插件与托管服务检查，**没有自动执行整套 `test:host` 或 tarball 的 Web profile 验收**。这些目前是维护者的合并／发布前检查，不能描述成已存在的自动门禁。

建议下一步增加独立的真实宿主 job：Linux + Node 24，矩阵只放精确最低／推荐版本及提交，checkout 并构建对应未打补丁的宿主，然后加载插件构建产物运行组合回归；保留 tarball 独立安装步骤。宿主缓存按 OS、Node、精确提交和 lockfile 区分。完整 Web 交互可先保留为发布前人工验收，稳定后再自动化。

可选的上游开发分支观察 job 与必过矩阵分开，失败必须可见并在验证记录中解释；不能给已承诺版本的必过 job 设置 `continue-on-error`。本约定没有新建定时任务或自动扩大支持版本。

## 发布证据模板

每次发布创建 `docs/validation-YYYY-MM-DD-<插件版本>.md`，至少写入：

```text
插件版本与提交；tarball 文件与 SHA-256：
宿主精确版本、标签与提交；是否未打补丁：
OS／架构、Node 与 pnpm：
类型检查／单元测试／构建：命令、结果、日志或 CI 链接
真实组合测试：命令、结果
发布包安装与 Web 卡片：profile、步骤、结果
托管生命周期与真实搜索：分别记录结果
官方备用能力及行为：
跳过、失败、未覆盖项及原因：
```

证据对应具体插件构建与宿主组合。历史验证可以证明历史版本行为，不能自动证明新发布通过。支持范围外的 CPU 架构、发行版、旧宿主与新候选不得写成已验证。
